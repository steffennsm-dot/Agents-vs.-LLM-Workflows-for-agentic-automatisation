\section{Final TADF and Demonstration}
\label{sec:TADF/final}

This chapter presents the final  TADF for this thesis, and demonstrates it on a task, as in the demonstration activity of DSRM \parencite{peffersDesignScienceResearch2007}. Section~\ref{subsec:TADF/artifact} describes its structure, its iterative development and its procedure, illustrated by the monthly invoice creation. Section~\ref{subsec:TADF/objective-results} compares the design objectives with the results.

\subsection{The Final TADF}
\label{subsec:TADF/artifact}

The final TADF~v3 is a skill for an LLM assistant, that is, a reusable set of instructions, reference documents and a template. For each task, it recommends deterministic implementation, an LLM workflow for orchestaration, an agent for orchestaration or decomposition. For an LLM workflow or an agent, it adds the design knowledge needed to build it. It keeps the two stages of the Decision Sheet: gates first, then a weighted comparison (Section~\ref{subsubsec:TADF/framework}). The work is divided by what each role does reliably. The software architect describes the tasks with its charecteristics and the deployment context and sets the priorities. The Skill with the LLM assistant interprets the descriptions, proposes answers and explains the result. Code applies the fixed rules. 

\subsubsection{Structure}
\label{subsubsec:TADF/artifact-form}
\label{subsubsec:TADF/artifact-documents}

Figure~\ref{fig:tadf-structure} shows the parts of TADF~v3 and how they work together. It also shows how the scope of \ref{sec:Intro} is reached. \path{SKILL.md} specifies the procedure and summarizes the rulebook. \path{assets/window.html} is the consultation window, an interactive page whose code applies the rules. The LLM fills the window with the tasks and its proposed answers and shows it in the chat. The architect answers by click, and the window sends the result back to the chat. Three reference documents form the rulebook. \path{evidence-and-scoring.md} holds the evidence behind each gate, the fixed capability scores and the calculation rules. \path{design-knowledge.md} holds the implementation guidance, including the mandatory minimum for LLM workflows. \path{constructs-and-scope.md} defines a task, the two orchestration paradigms and the terms that make human approval mandatory, and it states the scope. Where \path{SKILL.md} or the window differs from the references, the references apply.

\caption[Decision flow and structure of the final TADF.]{Decision flow and structure of the final TADF (v3).}

The window has nine sections: Task, Context, Gates, Task fit, Priorities, Commitment, Live result, Design knowledge and Finish. For each task, its code determines the route and both totals. It applies the exclusions by mandatory markings, the tie and close-call rules and the limit of two split-or-simplify operations per task lineage, lists the required components and controls and names a leading build form. Route and totals change as soon as an answer changes. The window needs a host that can show interactive pages in the chat, such as the Claude or ChatGPT app. Elsewhere, \path{text-mode.md} asks the same questions as text. \path{headless-mode.md} decides without questions, for batch runs and in the benchmark mode of Episode~2.

\subsubsection{Iterative Development}
\label{subsubsec:TADF/artifact-correction}
\label{subsubsec:TADF/artifact-provenance}
TADF was developed in iterations. In DSR, building and evaluating typically alternate several times before the final artifact emerges \parencite{hevnerDesignScienceInformation2004}. After an evaluation, the researchers can return to design and development to improve the artifact \parencite{peffersDesignScienceResearch2007}. Each iteration of TADF started from a finding, changed the framework, checked the change and recorded it in a dated entry of the development log (Appendix~\ref{app:repository/audit}). Before each evaluation, the current state was frozen, so every result refers to a fixed version. The form of TADF changed three times (Appendix~\ref{app:artifact/versions}). After the experiments (Section~\ref{subsec:TADF/design}), it began as an ordered list of routing questions, also drawn as a decision tree and a decision table. It then became the Decision Sheet, an Excel workbook that practitioners assessed in Episode~1 (Sections~\ref{subsec:TADF/initial-artifact} and~\ref{subsubsec:TADF/episode1}). Their feedback turned it into a skill for an LLM assistant with a text consultation, which Episode~2 evaluated on WorkBench (Section~\ref{subsubsec:TADF/episode2}). In its final state, the skill runs the consultation in one window, with a text mode and a headless mode for other uses.

The most important changes after Episode~2 illustrate these iterations; the development log describes all of them (Appendix~\ref{app:repository/audit}). G4 now asks whether the planned reads show everything the decision needs, because some searches return at most five records. Every LLM workflow now comes with the mandatory minimum, because the first LLM workflow had lacked components that the design knowledge prescribed (Section~\ref{subsubsec:TADF/episode2}). Retrieval success (T3) and extraction success (T2) were removed, because their evidence did not hold, and their content remains in the design knowledge (Section~\ref{subsubsec:TADF/evolution}). Finally, the consultation moved from a text dialogue into one interactive window, in which code applies the rules and is tested against the rulebook (Appendix~\ref{app:artifact/files}). In test consultations, this cut the consultation time by about 75 to 80 percent, from 15.2 to 3.8 minutes for a single task and from 38.1 to 7.9 minutes for a system with several tasks.

\subsubsection{Procedure and Operation: Monthly Invoice Creation}
\label{subsubsec:TADF/artifact-procedure}
\label{subsec:TADF/demonstration}
\label{subsubsec:TADF/demonstration-run}

The final TADF is demonstrated with Claude Sonnet~5.5 in the Claude app. It shows how the final TADF leads from a description to a checked recommendation with design knowledge. The example is the monthly invoice creation of a freelancer, a task that played no part in the development. The freelancer records the work for each client in a Notion table. At the end of the month, the task rewords these notes into invoice line items, fills one template with the client data, the line items and the total, and saves the draft in a folder for review. Sending stays manual. Figures~\ref{fig:demo-window-head} to~\ref{fig:demo-window-result} show the window in three parts.

A consultation starts with the architect's own description of the system and its tasks. This follows the interviews, in which participants wanted to start from their own description of a process and let an assistant derive the assessment (P05, P06, P11, P12). From this description, the assistant fills the window with one tab per task and proposes an answer wherever the description gives evidence, with the reason below it (Figure~\ref{fig:demo-window-head}). A bar at the top shows the route, both totals and the number of open answers. The section Task holds the description, the answer to the open question TQ0: ``Describe the task in your own words: what is the goal, and how does it run, step by step?'' The section Context records lifecycle and maturity, which shape only the design knowledge. Its approval questions decide whether a person must approve before the task acts. The invoice draft is held for review, so it is not a consequential action, and no approval is required.

\begin{figure}[htbp]
\centering
\includegraphics[width=.98\linewidth]{Figures/Vorschau_Testdaten_fig_demo_window_part1.png}
\caption[Final TADF consultation window part 1.]{Final TADF consultation window for the invoice task, part 1: task tab, live bar, task description and context with the proposed answers and their reasons.}
\label{fig:demo-window-head}
\end{figure}

The section Gates holds the five gates in fixed order (Figure~\ref{fig:demo-window-gates}). The first gate that fires decides the route, answers that fire a gate are marked, and questions that a fired gate makes irrelevant are hidden. G1 asks whether the task needs an LLM. The client-facing text does, while reading the entries, filling in the client data, calculating the total and saving the file stay plain code in the build. G2 asks whether the task is one LLM job, and G3 whether one pass can meet it reliably. G4 asks whether every next step can be fixed before the run and whether the planned reads show everything the decision needs. Here, the next step never depends on what a read returns, and the architect confirmed that the reads return all entries of a month despite pagination. G5 asks whether the sources are fixed in advance. No gate fired, so T1 and the weights decided. T1 did not apply, because rewording notes needs judgment. The architect weighted safe failure (P2) and schema guarantee (P3) as critical (3), traceability (P1) and robustness to messy input (P5) as important (2), and cost (P4) and evolvability (P6) as nice to have (1), and set latency to 0. A weight left open counts as 2, and only the architect can mark a weight as mandatory. The section Commitment asks whether the build will implement the mandatory minimum, and the architect committed to it.

\caption[Final TADF consultation window part 2.]{Final TADF consultation window part 2: the five gates, task fit, the weights of P1--P6 and the commitment to the mandatory minimum.}

The section Live result shows the route and its calculation (Figure~\ref{fig:demo-window-result}). With these answers, the LLM workflow led by 32 to 24 points. Safe failure, schema guarantee and traceability outweighed the agent's lead in robustness to messy input and evolvability. The window named the canonical two-stage form as the leading build form to prototype first. The component rule made an input normalization stage mandatory (P5) and recorded evolvability as an accepted limitation (P6). The section Design knowledge gives the four categories in short form: environment, build form, build rules and model check. The section Finish states the boundary of TADF: the order of tasks, triggers, hand-offs and interfaces stay with the architect.

With ``Send result to chat'', the window sends the answers, the result and the calculation to the chat, together with a line that holds the complete task entry, from which the window can be rebuilt. Sending also confirms the proposals left unchanged. The architect kept 18 of the 19 proposed answers and set robustness to messy input to 2 instead of 3.  The full design knowledge, the decision record and an architecture map can follow on request, and the architect can ask in the chat about evidence, definitions or how sure a decision is.


\subsection{Results Against the Design Objectives}
\label{subsec:TADF/objective-results}
\label{subsubsec:TADF/demonstration-summary}

The results support most design objectives of TADF, but to different degrees. They support the decision core (O1 to O3) and the grounding in workplace tasks (O8). They support reproducibility (O4), implementation knowledge (O6) and bounded effort (O7) in part. They do not establish measurably better decisions on new tasks (O5). Following the evaluation activity of DSRM \parencite{peffersDesignScienceResearch2007}, this section compares each design objective with the observed results, in the three categories of Section~\ref{subsec:TADF/objectives}. Table~\ref{tab:result-summary} in Appendix~\ref{app:artifact/objective-results} lists the results with their sources. Section~\ref{subsec:discussion/limitations} sets out the limits of these results.

The decision core is well supported. O1 requires a complete and structured decision space. TADF offers four routes, decided by five ordered gates and a weighted comparison, and it states its scope. Among 20,000 random answer sets, the window code returned each of the four routes, and the text consultation of the CrewAI email scenario reached all four (Appendix~\ref{app:transcripts/audit}). Tasks outside the scope were not tested. O2 requires decisions based on structural task characteristics known in advance. The gates and T1 ask for such characteristics, and the experiments show that they matter. Where later actions depended on earlier outcomes, the agent solved 13 of 15 executions and the LLM workflow none. Where written rules decided, the LLM workflow returned the reference decision in all 75 executions and the agent in 60. In Episode~1, participants used the same characteristics in their rules of thumb (P02, P03, P06, P07). In the window consultations, the architect kept 58 of the 64 answers that the assistant proposed from the descriptions (Appendix~\ref{app:transcripts/window}). O3 requires that each recommendation names its empirical evidence. Each gate and capability score of TADF names its basis, mostly results of the experiments (Appendix~\ref{app:artifact/provenance}). Where evidence is missing, TADF says so, for example for evolvability (P6) and the third G3 condition.

Decision quality has the weakest support. O4 requires that identical task characteristics, constraints and priorities yield the same recommendation and that its reasoning can be reconstructed. In TADF, code applies the fixed rules, and each result shows its calculation. Tests showed that the window reproduces every route, total and control of the text consultations and agrees with an independent implementation of the rule text on 20,000 random answer sets. Both WorkBench passes also gave the same 69 recommendations. This support is narrow, because all 69 were LLM workflows under the default weights and repeated consultations were not tested. O5 requires a better trade-off between task success and token cost than one orchestration paradigm for all tasks. On the development data, the Decision Sheet matched the success of Always agent, 82.5 percent, with 47 percent fewer tokens per successful execution. On WorkBench, however, TADF recommended the LLM workflow for all 69 templates, and no gate fired. Routing therefore equaled Always LLM workflow at 66.2 percent. It was more successful than Always agent in all four configurations but less successful than Oracle at 75.9 percent. Measurably better decisions on new tasks thus remain unestablished.

Use and deployment show a mixed picture. O6 requires task-specific implementation knowledge with each recommendation. TADF adds design knowledge to each recommended LLM workflow or agent and requires the mandatory minimum for every LLM workflow. In Episode~2, LLM workflow v2.1, which implemented parts of this design knowledge, raised task success from 41.6 to 66.2 percent. The effect of single rules and build forms was not tested. O7 requires that software architects can understand and apply TADF with bounded effort. Five participants of Episode~1 supported an LLM assistant or skill that they could use directly in their work (P05, P06, P08, P11, P12). TADF~v3 is therefore a skill, and its window cut the consultation time by about 75 to 80 percent (Section~\ref{subsubsec:TADF/artifact-correction}). Use by architects other than its builder was not tested. O8 requires realistic workplace tasks and a stated scope. The experiments used 120 task instances of eight task archetypes from 13 of 48 benchmark sources. Episode~2 used the 690 task instances of WorkBench in five domains, and the demonstration used the invoice task and the CrewAI email scenario. The rulebook states the scope (Section~\ref{subsubsec:TADF/artifact-form}).
